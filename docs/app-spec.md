# Open Cinema director app: specification

This file is the contract for the web app in `app/`. The acceptance scripts (`scripts/accept_app_*.py`) check exactly what is written here, so names, routes, test ids and numbers below are fixed. Do not edit this file; if something in it is wrong or impossible, file a bead and work around it as closely as you can.

The app is a director's console: describe a shot, choose the camera, lens, aperture and framing, generate it with LTX-2 in ComfyUI, run the Open Optics chain on the result, then watch it with a before/after slider and change the aperture without regenerating.

## 1. Architecture

```
browser  --HTTP/SSE-->  app server (Python, aiohttp)  --Comfy SDK-->  comfy-api-proxy  -->  ComfyUI :8188
```

- `app/` is a Python package, started with `python -m app` from the repository root. It uses only: the standard library, `aiohttp`, `comfy_sdk` (the Comfy SDK), `comfy_api_proxy` and `open_optics` (the core library, for the framing helper). The frontend is plain HTML, CSS and JavaScript (ES modules) in `app/static/`, with no build step, no npm packages and nothing loaded from the internet (no CDN, no web fonts).
- All ComfyUI traffic goes through the Comfy SDK (`comfy_sdk.Comfy` or `AsyncComfy`): `client.workflows.from_json(graph)`, `client.assets.from_file(path)` + `wf.set_input(node_id, "file", asset)`, `client.submit(wf)`, `job.events()`, `job.get_outputs(node_id)[0].to_file(path)`, `job.cancel()`. The SDK talks to `comfy-api-proxy`, which the app starts itself, inside its own process and event loop (`comfy_api_proxy.app.make_app(comfyui_url)` served with an `aiohttp.web.AppRunner` on `127.0.0.1`, port `--proxy-port`, default 0 = any free port), and points the SDK at it with the `COMFY_BASE_URL` environment variable. With `--proxy-url URL` the app uses an already running proxy instead and starts none.
- The SDK reports progress through the proxy at most about twice a second, and a short run gives only a few `Progress` events: derive status and progress from status changes and node ids as well, and never depend on a count of progress events.
- The SDK is blocking: run it in worker threads (`asyncio.to_thread` or one thread per shot), never on the event loop.
- Command line (`python -m app --help` lists it): `--comfyui URL` (default `http://127.0.0.1:8188`), `--host` (default `127.0.0.1`), `--port` (default 8000), `--proxy-port` (default 0), `--proxy-url`, `--data-dir` (default `app/data`, ignored by git). On start it prints one line: `Open Cinema is running at http://HOST:PORT (ComfyUI at URL)`. It starts even when ComfyUI is not running.
- Shots are stored on disk in `DATA_DIR/shots/<id>/` (`shot.json` plus the videos), so they survive a restart. After a restart a shot that was still queued, generating or in optics becomes `failed` with error code `interrupted`.
- One shot runs at a time. Shots submitted meanwhile wait with status `queued` and start in submission order.

## 2. The shot

Parameters (JSON field: allowed values):

| field | values |
|---|---|
| `description` | string, 3 to 1000 characters after trimming |
| `camera` | `static`, `dolly-in`, `dolly-out`, `pan-left`, `pan-right`, `tilt-up`, `orbit`, `handheld` |
| `lens_mm` | 24, 35, 50, 85 |
| `aperture` | one of the stops 1.4, 2, 2.8, 4, 5.6, 8, 11, 16 |
| `framing` | `close-up`, `waist-up`, `full-body`, `wide` (labels: Close-up, Waist-up, Full body, Wide) |
| `seed` | optional integer 0 to 2147483647; default random |

Camera labels: Static, Dolly in, Dolly out, Pan left, Pan right, Tilt up, Orbit, Handheld.

### 2.1 Subject distance from the framing

The distance comes from `open_optics.framing` (do not re-implement the formula). Image 1280 x 704, sensor width 36 mm, so `sensor_height_mm(36, 1280, 704)` = 19.8 mm. The subject is a person, real height 1.7 m. `SUBJECT_HEIGHT_FRACTION` is how much of the frame height the person's full 1.7 m height would span (above 1 means the framing crops the person):

| framing | fraction |
|---|---|
| close-up | 2.8 |
| waist-up | 1.6 |
| full-body | 0.85 |
| wide | 0.35 |

`subject_distance_m(lens_mm, 19.8, fraction * 704, 704, 1.7)`. Hand-checked results in metres (rounded to 4 decimals):

| lens | close-up | waist-up | full-body | wide |
|---|---|---|---|---|
| 24 | 0.7599 | 1.3119 | 2.4482 | 5.9114 |
| 35 | 1.1082 | 1.9132 | 3.5704 | 8.6209 |
| 50 | 1.5832 | 2.7331 | 5.1005 | 12.3155 |
| 85 | 2.6914 | 4.6462 | 8.6709 | 20.9364 |

Example by hand: 50 mm, full body: h = 19.8 x 0.85 = 16.83 mm on the sensor, u = 50 x (1 + 1700 / 16.83) = 5100.5 mm = 5.1005 m.

### 2.2 The LTX-2 prompt

`app/shot.py` has `build_prompt(params) -> str`:

`"{FRAMING_PHRASE}. {description} {CAMERA_PHRASE}. {lens} mm lens look, deep focus with everything sharp from the foreground to the far background, cinematic lighting, 35mm film."`

where `description` is trimmed and gets a final `.` if it does not already end in `.`, `!` or `?`, and the phrases are:

| framing | phrase |
|---|---|
| close-up | Close-up shot of the subject's face and shoulders |
| waist-up | Waist-up medium shot |
| full-body | Full-body shot, the whole figure visible head to toe |
| wide | Wide establishing shot, the figure small in a large scene |

| camera | phrase |
|---|---|
| static | The camera is locked off and does not move |
| dolly-in | Slow dolly-in toward the subject |
| dolly-out | Slow dolly-out away from the subject |
| pan-left | Smooth pan to the left |
| pan-right | Smooth pan to the right |
| tilt-up | Slow tilt up |
| orbit | The camera orbits slowly around the subject |
| handheld | Handheld camera with subtle natural movement |

The video is generated sharp on purpose ("deep focus"): the depth of field comes from the optics stage and the chosen aperture, which is why the aperture can be changed afterwards.

## 3. ComfyUI graphs (`app/graphs.py`)

Both builders return API-format graphs (`{node_id: {"class_type", "inputs"}}`) that pass `tests.fake_comfy.validate_prompt(graph, input_files=[...])`, which checks them against the real node definitions recorded from ComfyUI 0.41.0 in `tests/fixtures/app/comfy_object_info.json`. Inputs whose names contain a dot, like `output.normalization`, are ComfyUI dynamic-combo sub-inputs and are written with the dotted name in the graph (`"output": "depth", "output.normalization": "raw", "output.apply_sky_clip": false`). Node ids are fixed strings, so ComfyUI's execution cache recognises unchanged nodes between runs.

- `build_generation_graph(prompt: str, seed: int, prefix: str) -> dict`: the LTX-2 19B distilled Q4_K_M two-stage pipeline exactly as in `bench/workflows.py` `ltx2_19b_q4` (8 distilled steps at 640x352, x2 latent upscale, 3 refine steps at 1280x704, 121 frames at 24 fps, audio and video, text encoder device `default`), but with its own code in `app/graphs.py` (the app must not import `bench`). `CLIPTextEncode.text` is the prompt, `RandomNoise.noise_seed` is the seed (the second stage uses seed + 378), `SaveVideo.filename_prefix` is the prefix. Module constant `GENERATION_OUTPUT_NODE` is the id of the `SaveVideo` node.
- `build_optics_graph(video_file: str, focal_mm: float, f_number: float, subject_m: float, prefix: str) -> dict`: `LoadVideo(file=video_file)` -> `GetVideoComponents` -> `LoadDA3Model` (`depth_anything_3_mono_large.safetensors`, weight_dtype `default`) -> `DA3Inference` (resolution 504, `upper_bound_resize`, mode `mono`) -> `DA3Render` (output `depth`, `output.normalization` `raw`, `output.apply_sky_clip` false) -> `OpenOptics_DepthToMetric` (`depth_image` from DA3Render, `mode` `subject`, `subject_m`, `subject_x` 0.5, `subject_y` 0.5, `inverse_depth` false, `near_m` 0.3, `far_m` 80, `low_percentile` 2, `high_percentile` 98) -> `OpenOptics_DepthTemporalSmooth` (`depth` from the `MASK` output, `strength` 0.7) -> `OpenOptics_DepthOfField` (`image` from GetVideoComponents, `depth_mask` from the smooth node, `focal_mm`, `f_number`, `focus_m` = `subject_m`, `sensor_width_mm` 36, `max_radius_px` 24, `quality` `normal`, `colorspace` `srgb`) -> `CreateVideo` (images from DepthOfField, `audio` from GetVideoComponents output 1, `fps` from GetVideoComponents output 2) -> `SaveVideo` (`filename_prefix` = prefix, `format` `auto`, `codec` `auto`). Module constant `OPTICS_OUTPUT_NODE` is the id of the `SaveVideo` node.
  - Between two calls that differ only in `f_number` and `prefix`, every node except `OpenOptics_DepthOfField`, `CreateVideo` and `SaveVideo` must have identical inputs, so a re-apply costs one Depth of Field pass and not another depth estimation.
- `app/shot.py`: `SUBJECT_HEIGHT_FRACTION` (dict as above), `subject_distance(lens_mm, framing) -> float` (metres, unrounded), `build_prompt(params)`, `validate_shot(data) -> dict` (returns the cleaned params, raises `ShotError` with `.field` and `.message`), `CAMERAS`, `LENSES`, `APERTURES`, `FRAMINGS`.

## 4. HTTP API

Errors are JSON `{"error": {"code": str, "message": str, "field": str|null}}`. `message` is a full sentence a user can read.

| route | behaviour |
|---|---|
| `GET /` | `app/static/index.html` |
| `GET /static/...` | the files in `app/static/` |
| `GET /api/health` | always 200: `{"app": "ok", "comfyui": {"url": str, "reachable": bool, "device": str\|null, "message": str\|null}}`. Reachable means `GET {comfyui}/system_stats` answered within 2 s; `device` is the first device's name. The health check uses a connect timeout of at most 1 s inside the 2 s total (on Windows a refused loopback connection takes about 2 s to fail otherwise, which would make a cold start slow). When not reachable `message` is `"Can't reach ComfyUI at <url>. Start ComfyUI, then retry."` |
| `GET /api/options` | `{"cameras": [{"id","label"}], "lenses": [24,35,50,85], "apertures": [1.4,...,16], "framings": [{"id","label"}], "defaults": {"camera": "static", "lens_mm": 50, "aperture": 2.8, "framing": "full-body"}}` |
| `GET /api/estimate?lens_mm=50&framing=full-body` | `{"subject_distance_m": 5.1005, "sensor_height_mm": 19.8, "subject_height_fraction": 0.85, "real_height_m": 1.7}` (distance rounded to 4 decimals); 400 `invalid_shot` for bad values |
| `POST /api/shots` | body = shot parameters. 201 + the shot record. 400 `invalid_shot` (with `field`). 503 `comfy_unreachable` when ComfyUI cannot be reached at that moment (no shot is created) |
| `GET /api/shots` | `{"shots": [record, ...]}`, newest first (ordered by creation; two shots created in the same second keep their creation order) |
| `GET /api/shots/{id}` | the record; 404 `not_found` |
| `GET /api/shots/{id}/events` | Server-Sent Events: first an `event: shot` frame with the current record, then one for every change (progress changes at most about 5 times per second), ending after the shot reaches `done`, `failed` or `cancelled` (the stream also ends for a shot that already is in such a state, after its one frame). A comment line every 15 s as keep-alive |
| `POST /api/shots/import` | multipart form: `file` (.mp4 or .webm, at most 200 MB), `lens_mm`, `aperture`, `framing`, optional `name`. The video becomes the shot's "before" and only the optics graph runs on it (no LTX-2, so no generation models are needed). 202 + record (status `optics`, `imported: true`, description `Imported clip: <name>`, camera `static`). 400 `invalid_shot` (field `file`, `lens_mm`, `aperture` or `framing`); 413 `too_large`; 503 as for `POST /api/shots`, checked against the optics graph only |
| `POST /api/shots/{id}/reapply` | body `{"aperture": 5.6}` (a stop). Runs only the optics graph again on the stored "before" video. 202 + record (status `optics`). 404; 400 `invalid_shot`; 409 `not_ready` if the shot has no before video; 409 `busy` if it is queued, generating or in optics (checked in this order: 404, 400, `not_ready`, `busy`) |
| `POST /api/shots/{id}/cancel` | cancels a queued, generating or optics shot (`job.cancel()`); 200 + record with status `cancelled` (the before video, if there is one, stays); cancelling a re-apply of a shot that already has a version puts the shot back to `done` instead; 409 `not_running` otherwise |
| `DELETE /api/shots/{id}` | 204; removes the record and files; 409 `busy` while running |
| `GET /media/{id}/{name}` | the stored video, with `Content-Type` from the extension and HTTP Range support (206) |

### 4.1 The shot record

```json
{
  "id": "20261019-221530-ab12",
  "created_at": "2026-10-19T22:15:30Z",
  "params": {"description": "...", "camera": "dolly-in", "lens_mm": 50, "aperture": 2.8, "framing": "full-body", "seed": 123},
  "derived": {"subject_distance_m": 5.1005, "prompt": "..."},
  "status": "queued | generating | optics | done | failed | cancelled",
  "progress": 0.0,
  "message": "Generating video: step 3 of 8",
  "stages": [
    {"id": "generate", "label": "Generate video", "state": "pending | active | done | failed", "progress": 0.0},
    {"id": "optics", "label": "Apply optics", "state": "pending | active | done | failed", "progress": 0.0}
  ],
  "elapsed_s": 12.4,
  "error": null,
  "reapply_error": null,
  "before_url": null,
  "versions": [{"n": 1, "aperture": 2.8, "url": "/media/<id>/after_1.mp4", "created_at": "..."}],
  "current_version": 1
}
```

- `progress` is overall, 0 to 1, never decreases during one run, and is 1 when `done`. Generation counts for the first 85 % and optics for the rest in a first run; in a re-apply `progress` covers the optics stage alone (0 to 1) and the `generate` stage stays `done`.
- `message` is a short human line for the status panel ("Waiting for ComfyUI", "Generating video: step 3 of 8", "Estimating depth", "Applying depth of field", "Done"); update it from the SDK `Progress`/`StatusChange` events (`current_node` tells which graph node is running).
- `elapsed_s` counts from when the shot started to now (or to the end).
- `error`: `null`, or `{"code", "message", "stage"}` when `status` is `failed`, where `code` is one of `comfy_unreachable` (ComfyUI could not be reached, also when it stops during a run; give up after at most 30 s), `comfy_rejected` (ComfyUI refused the graph, e.g. a model or custom node is missing; `message` includes ComfyUI's own text), `job_failed` (a node failed in ComfyUI; `message` includes the node type and ComfyUI's message), `download_failed`, `interrupted`, `internal`. `stage` is `generate` or `optics` (for `interrupted`: the stage that was running; `generate` if the shot was still queued).
- A failure in the optics stage after generation succeeded keeps `before_url`; the shot is `failed` but can be retried with `reapply`. A failure in a re-apply of a shot that already has versions does not change its status: it stays `done`, `reapply_error` holds the same object as `error` and is cleared by the next successful re-apply.
- `versions` grows by one with each successful optics run; `n` starts at 1; `current_version` is the latest `n`, `null` before the first. Video file names: `before.<ext>`, `after_<n>.<ext>`, with the extension of the file ComfyUI produced.
- The first optics run uses the shot's own `aperture`; its subject distance is `derived.subject_distance_m`.

### 4.2 What goes to ComfyUI (checked by the tests through the fake server)

1. Generation: `build_generation_graph(derived.prompt, seed, f"opencinema/{id}/before")`, submitted with the SDK; the `SaveVideo` output is downloaded into the shot folder as `before.<ext>`.
2. Optics: the before video is uploaded with `client.assets.from_file(...)` and set as the `file` input of `LoadVideo`; `build_optics_graph(file, lens_mm, aperture, derived.subject_distance_m, f"opencinema/{id}/after_{n}")`; the `SaveVideo` output is downloaded as `after_<n>.<ext>`.
3. Re-apply: the same optics graph with the new `f_number` only. ComfyUI then reuses the cached depth nodes; the LTX-2 nodes do not run at all.

## 5. The interface

One page, `app/static/index.html`, with `app.css` and ES modules. It works in current Chromium at 1280 x 720 and larger without page scrolling (section 5.3). Every element below has a `data-testid`; the tests find things only by these, plus roles and visible text where stated.

### 5.1 Elements

Header: `app` (root element), `comfy-status` (`data-state` = `checking`, `ok` or `down`; text `ComfyUI: connected` + device name, `ComfyUI: offline`, or `ComfyUI: checking`), `comfy-banner` (only when down; `role="alert"`; text: the health `message` and, as a button `comfy-retry` labelled "Retry", a re-check; it disappears when ComfyUI is reachable). The app re-checks health every 5 s while down, every 30 s otherwise, when the window gets `focus` or the tab becomes visible, and right after a request to the app server failed because ComfyUI could not be reached (the 503 `comfy_unreachable` of a submit turns the header into `down` and shows the banner at once).

Director panel (left):
- `shot-description`: `<textarea>`, label "Scene", placeholder an example shot, `maxlength` 1000. Ctrl+Enter generates.
- `camera-group`, `lens-group`, `framing-group`: elements with `role="radiogroup"` and an accessible name ("Camera move", "Lens", "Framing"); each option is a `<button role="radio" data-value="...">` with `aria-checked`; arrow keys move the selection inside a group; exactly one option is checked. The values are the ids in section 2; lens buttons are labelled "24 mm" etc. Defaults from `/api/options`.
- `aperture-slider`: `<input type="range" min="0" max="7" step="1">` over the stops 1.4, 2, 2.8, 4, 5.6, 8, 11, 16 (index 0 to 7), with `aria-valuetext` "f/2.8"; `aperture-value`: text "f/2.8" (stops 2, 4, 8, 11, 16 are written f/2, f/4, f/8, f/11, f/16).
- `subject-distance`: text "Subject about 5.1 m" (one decimal; below 10 m, one decimal; 10 m or more, no decimals) with attribute `data-metres` set to the `/api/estimate` value; it updates when the lens or framing changes.
- `generate-button`: text "Generate shot". Disabled while the description (trimmed) is shorter than 3 characters, while ComfyUI is down, and while a shot of this page is queued, generating or in optics. Enabled otherwise.

Monitor (right):
- `viewport`: 20:11 box, `data-state` = `empty` (nothing yet, shows a short hint), `working` (a shot is queued, generating or making its first optics pass, or has just been submitted), `result` (a finished shot, also while a re-apply runs), `failed`, `cancelled`. It contains four `crop-mark` elements (the corner brackets) and, while working, a `record-dot`. It also contains `hud`, a camera-style overlay with text like `50 mm  f/2.8  5.1 m  FULL BODY` (lens, aperture, distance, framing); it follows the form while editing and shows the shot's values when a shot is shown.
- `status-panel` (visible when `working`, `failed`, `cancelled`): `data-status` = the record's status; `status-label` (the record's `message`), `progress-bar` (`role="progressbar"`, `aria-valuenow` 0 to 100), `stage-generate` and `stage-optics` (`data-state` = the stage state), `elapsed` (`m:ss`), `cancel-button` (labelled "Cancel", only while queued, generating or in optics).
- `error-message` (`role="alert"`, in `failed` state; shows `error.message`) and `retry-button` ("Retry optics" if the shot has a before video, else "Try again", which submits the same parameters as a new shot). In `cancelled` state the `status-label` reads "Cancelled." and `retry-button` reads "Try again".
- `player` (in `result` state): `before-video`, `after-video` (both `<video>`, `muted`, `playsinline`, `loop`, same size, stacked), `compare-slider` (`role="slider"`, `aria-label="Before and after"`, `aria-valuemin` 0, `aria-valuemax` 100, `aria-valuenow` = the divider position in percent from the left; the left of the divider shows the before video, the right shows the after video; arrow keys move it by 1, with Shift by 10, Home and End jump to 0 and 100; dragging the handle `compare-handle` with the mouse moves it; default 50), `label-before` ("Before"), `label-after` ("After f/2.8" with the version's aperture), `play-toggle` (button, `aria-pressed`, Space also toggles when the player has focus), `scrubber` (`<input type="range" min="0" max="1000">`), `time-readout` (`0:02 / 0:05`). Both videos always play together (their `currentTime` differ by less than 0.25 s).
- Optics controls (in `result` state): `reapply-slider` (same stops as the aperture slider, starts at the shown version's aperture), `reapply-value` ("f/5.6"), `reapply-button` ("Apply aperture"; disabled while the slider is at the aperture of the shown version and while a re-apply runs), `reapply-status` (text: "Applied f/2.8", "Applying f/8 ...", or the re-apply error message), `version-list` with one `version-chip` per version (a button labelled "f/2.8", `data-version`, `data-aperture`, `aria-pressed` for the shown one; clicking shows that version in `after-video` and moves `reapply-slider` to it). A re-apply uses the generic status of the shot (status `optics`, record updates over SSE) but the player stays visible and playable; when it finishes the new version is shown.

History (bottom strip): `history-list` containing `history-item` entries, newest first (`data-shot-id`, `data-status`), each with a short title (the first 40 characters of the description), the lens, aperture and framing, and a status dot; clicking one shows that shot (and follows it live if it is running). `history-new` ("New shot") clears the viewport to the empty state and focuses the description. After a page reload the latest shot is shown again (and followed if it is still running).

### 5.2 Behaviour

- Generate: POST the form; on 503 or any error show the message in a banner or `error-message` (an error toast is fine as long as it has `role="alert"` and the server's message); on 201 follow the record over `EventSource` (`/api/shots/{id}/events`); `viewport` goes to `working`, then `result` when `done`, `failed` on failure. If the event stream drops, reconnect and fall back to polling `GET /api/shots/{id}`.
- While working, the player and form stay usable except for Generate. Changing the form never affects a running shot.
- Cancel: POST cancel; the viewport goes to `cancelled` (status panel with "Cancelled." and a "Try again" button).
- Re-apply: `reapply-button` POSTs `/api/shots/{id}/reapply`; the shot goes through `optics` and back to `done`; a new `version-chip` appears and is shown.
- Time and progress shown come from the record; the client does not invent progress.

### 5.3 Design

A dark, cinematic, camera-like interface, clean and modern. It is judged on these rules (all checked by `scripts/accept_app_design.py`) and by eye.

- Colours as CSS custom properties on `:root`: `--bg: #0b0c0e`, `--surface: #14161a`, `--raised: #1b1e24`, `--line: #262a31`, `--text: #e9e6df`, `--muted: #9097a2`, `--accent: #f5a524` (tungsten amber, for the primary action, the focus ring and the active states), `--ok: #5ad19a`, `--danger: #ff6b6b`. The page background is `--bg`. Body text and muted text have a contrast ratio of at least 4.5 : 1 on their background.
- Type: a system stack for text (`"Inter", "Segoe UI", system-ui, sans-serif`), a monospace stack for numbers and the HUD (`ui-monospace, "Cascadia Mono", Consolas, monospace`). Nothing is fetched from outside the app's own origin.
- Camera feel: the viewport has corner crop marks (viewfinder brackets), the HUD in monospace along its bottom edge, a blinking record dot while working, a thin focus/exposure scale drawn with CSS next to the aperture slider, and the lens options drawn as a segmented ring with the focal length in a large monospace figure. Subtle depth: 1 px lines, soft shadows, no gradients that look like a web template. Motion is short (150 to 250 ms) and disabled under `prefers-reduced-motion: reduce`.
- Layout at 1280 x 720, 1366 x 768, 1440 x 900 and 1536 x 864: no page scrollbar (the director panel may scroll inside itself), the Generate button visible without scrolling, the viewport at least 560 px wide, the history strip visible. The grid is: header (48 to 56 px), a left director panel (360 to 420 px wide), the monitor taking the rest, the history strip at the bottom (88 to 120 px). Below 900 px wide the columns stack and the page may scroll; there is no horizontal page scroll at any width from 360 px up.
- Accessibility: `<html lang="en">`, a `<title>`, every interactive element has an accessible name, a visible `:focus-visible` outline in the accent colour, everything reachable by keyboard in a sensible tab order, state is never shown by colour alone.
- The page makes no failed requests and logs no console errors in any state.

## 6. Testing

- `tests/fake_comfy.py` is a fake ComfyUI server (read its docstring). `tests/app_harness.py` starts it together with the real app as a subprocess on free ports (`AppHarness`). Both are fixtures: do not edit them or `tests/fixtures/app/`.
- Backend tests use the harness and the fake. Interface tests use Playwright (`playwright.sync_api`, Chromium, headless) against the harness, and click through the whole flow. Playwright and its browser are installed already in the project's `.venv`; do not try to install anything. The tests must not need a real ComfyUI, a GPU or the network, and must clean up the processes they start.
- Every test file you add runs under `npm test` (unittest) and must not skip. Keep the whole suite under a few minutes: the fake is fast, so wait for conditions (`expect`/`wait_for`/polling with a timeout), never for fixed sleeps longer than 100 ms.
